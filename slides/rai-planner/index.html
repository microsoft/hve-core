The RAI Planner is an HVE Core agent that helps a team plan a Responsible AI assessment for one AI system. It asks questions in six phases, keeps its progress in files and drafts backlog items for the gaps it finds. We'll cover what ships with it, how a session runs, and how to tailor it for your organization with HVE Builder instead of forking it. Product details describe HVE Core main at commit 7e2de1a, read on October 1, 2026. The planner first merged in March 2026 (PR 979). Both walkthroughs are scripted; neither is a recorded agent run.
01 / WHAT IT PROVIDES

A repeatable assessment your team can resume

Coverage

The same checks for every system

Seven NIST AI RMF trustworthiness characteristics and seven AI threat categories, applied to each AI component.

Continuity

Progress lives in files

state.json and one rai-plan.md keep answers, gates and IDs, so a new chat continues where you stopped.

Action

Gaps become backlog drafts

Evidence gaps turn into Azure DevOps work items or GitHub issues. Nothing is created until you confirm.

It plans; people approve. Its outputs aren't legal approval, compliance certification or regulatory sign-off.

Threat categories: data poisoning, model evasion, prompt injection, output manipulation, bias amplification, privacy leakage and misuse escalation.

Three properties make the planner useful beyond a single conversation. Coverage: every system is checked against the same seven NIST AI RMF trustworthiness characteristics and seven AI-specific threat categories. Continuity: answers, gate confirmations and threat IDs live in state.json and one rai-plan.md, so a fresh chat or a teammate can continue. Action: the evidence register drives draft work items in Azure DevOps or GitHub format. The banner repeats the planner's own disclaimer: its outputs are suggestions for qualified reviewers, not legal approval, compliance certification or regulatory sign-off.

03 / HOW IT WORKS / PHASE 2

Phase 2 sets the depth of the assessment

NIST references are AI RMF Measure subcategories. A custom framework with replaceDefaultIndicators: true brings its own indicators.

Try the buttons. The prohibited uses gate always runs first; if a listed use applies, the planner stops until you acknowledge it. Then it evaluates three indicators, each tied to NIST Measure subcategories and each with its own method: binary, categorical and continuous. The number of activated indicators suggests the depth: none is basic, one is standard, two or more is comprehensive. That's only a suggestion. Phase 2 is a hard gate, so you confirm the tier. The buttons illustrate the counting rule in this page; they don't run the planner.

03 / HOW IT WORKS / GUARDRAILS

The planner suggests; people decide

Disclaimer first and last

The CAUTION block appears before any question and again at exit points.

Hard gates

Depth tier, mapping scope and the backlog handoff wait for your confirmation.

Partial autonomy

Work items stay drafts until you confirm them, with secrets, credentials and PII removed.

Narrow writes

Only .copilot-tracking/rai-plans/. Security plans are read-only and application source is off limits.

Content is data

Web pages, handoff payloads and tool output are treated as data, not as instructions.

Licensing posture

NIST AI RMF can be quoted with attribution, the EU AI Act is paraphrased and ISO is cite-only.

The conformance suite includes a request to declare a system compliant. Its rubric expects the planner to decline.

These rules are instructions the agent follows, not enforced permissions. Review its changes as you would any agent's.

These guardrails are written into the agent, its identity instructions and the shared instructions it inherits. The disclaimer appears at the start and again at exit points. Hard gates hold the decisions that change later work. Work items default to partial autonomy: drafts that you confirm, sanitized of secrets, credentials, internal URLs and personal data. Writes are limited to the project folder, security plans are read-only and application source is off limits. Pages, payloads and tool output are treated as data. The licensing posture keeps standards text paraphrased where required. Finally, the conformance suite includes a scenario where a user asks the planner to declare a system compliant; the rubric expects it to decline. I'm citing the scenario, not a test result. Keep in mind that all of these are instructions to the agent, not enforced permissions, so review what it writes.

Everything so far is the general case: NIST AI RMF 1.0, a generic set of stakeholders and either backlog format. Most organizations have their own policy, prohibited uses, vocabulary and routing. The design already separates orchestration from knowledge; ADR 0007 lists evolving RAI guidance without editing agent bodies as a decision driver. So you can add your own skill and instruction alongside the planner and leave HVE Core's files as they are.
05 / EXTEND IT / NO NEW FILES

Start by supplying references at Phase 1

Five reference types, each with a destination

  • standardPhase 3 maps it alongside the active framework
  • risk-indicator-categoryPhase 2 adds it to indicator screening
  • prohibited-use-frameworkPhase 2 checks it in the prohibited uses gate
  • output-formatEvery phase applies it when writing artifacts
  • code-of-conductProvider policies, checked in Phases 2, 3 and 5

Layer or replace

Layering keeps NIST AI RMF as the baseline. replaceDefaultFramework: true swaps in your framework's characteristics.

Templates

Supply a document or Mural template and the planner keeps assessment-content.md aligned to it.

Reuse limit

Summaries stay in this workspace's tracking folder. Teammates and other repositories supply them again.

Before you author anything, use what the planner already accepts. In Phase 1 it asks for evaluation standards, risk indicator categories, prohibited-use frameworks, output formats and provider codes of conduct. It analyzes each through rpi-research, writes a summary to the shared references folder and records it in state.json. Each type feeds specific phases. You can layer a standard on NIST, which is the default and the pattern rai-standards recommends, or replace NIST entirely. Templates work too: supply a document or Mural template and the planner keeps an assessment-content.md aligned to it. The limit is reuse: these summaries live in one workspace's tracking folder, and someone has to supply them again elsewhere.

When the same references and rules recur, package them. This table follows HVE Builder's guidance and VS Code's activation rules. A skill holds reusable knowledge and loads when its description matches or you invoke it by name. An instruction with an applyTo pattern attaches whenever the agent writes a matching file, which is how the planner's own identity instructions load. A subagent helps only with isolated, high-volume work, and nothing loads it automatically. Rules that must always hold belong in enforced controls such as hooks, schemas or CI, because instructions only guide the model. If your phases differ, build a sibling planner on the shared planner base instead of editing this one. HVE Core's own table still lists prompt files for entry points, but VS Code now documents them as deprecated for Agent Host sessions, so prefer a skill.
05 / EXTEND IT / HVE BUILDER

HVE Builder writes the extension and reviews it

  1. ScopeTargets, modes and write boundary. Read the target workflow's contract first.
  2. BaselineCapture the current contract of anything it changes.
  3. AuthorWrite the complete candidate in one batch.
  4. ValidateRun local checks and close what they find.
  5. ReviewApply the rubric, itself or with HVE Builder Reviewer in a fresh context.
  6. ResolveVerify each finding, fix required ones, then recheck.

Precedence, highest first

  1. Host and platform safety controls
  2. Your explicit scope and acceptance criteria
  3. Matching repository instructions and schemas
  4. The HVE Builder base standard
  5. Sibling examples and preferences

An extension can add conventions. It can't widen writes or weaken safety.

Outcomes

PassReviseDeferredBlocked

Default modes combine create, improve and refactor. Review-only and validate-only requests leave source unchanged.

HVE Builder is a skill for writing and reviewing prompts, instructions, agents, subagents and skills. By default it combines create, improve and refactor. For an extension, the first step matters most: read the target workflow's skill or agent and capture how it discovers extensions and what it passes, before choosing an artifact type. It authors the complete candidate, runs local checks, then runs a review pass against its rubric, either itself or with the HVE Builder Reviewer in a fresh context. Reviewer findings are suggestions; the agent running HVE Builder verifies each one and owns every fix. The precedence list is the safety boundary for anything you add. Evidence for each run goes under .copilot-tracking/hve-builder.

06 / EXTEND IT / CHECKLIST

Add context without loosening safeguards

Do

  • ✓Name RAI Planner, the domain and the trigger in each description.
  • ✓Scope applyTo to the plans folder or one project's subfolder.
  • ✓Refer to rai-standards and rai-identity by name instead of copying them.
  • ✓Layer your standard on NIST unless you mean to replace it.
  • ✓Back must-hold rules with a hook, schema or CI check.
  • ✓Review with HVE Builder, and add eval scenarios for new behavior.

Avoid

  • ✕Rewording or removing the disclaimer, hard gates or partial autonomy.
  • ✕Writing outside .copilot-tracking/rai-plans/ or changing application source.
  • ✕Copying restricted standards text. ISO standards are cite-only.
  • ✕Editing installed HVE Core files to hold one team's rules.

The RAI Reviewer's framework list is fixed in its agent file. Adding a framework there changes HVE Core itself, so propose it upstream.

A short checklist for anything you add. Descriptions do the discovery work, so name RAI Planner, the domain and the trigger. Keep applyTo scoped to the plans folder, or to one project's subfolder if only some assessments need the convention. Refer to rai-standards and rai-identity by name rather than copying them, so HVE Core updates still reach you. On the other side: an extension adds context; it doesn't remove the disclaimer, hard gates or partial autonomy, and it doesn't widen where the planner writes. One limit to know: the RAI Reviewer's framework list is fixed in its agent file, so adding a framework there is a change to HVE Core itself.
