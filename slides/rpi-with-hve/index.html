A coding agent can read a lot and still miss the detail that matters. On a multi-file change, that might be a naming exception, a decision buried in chat or a check that ran against only one module. RPI gives the work separate research, planning, implementation and review steps, with files that let you inspect the reasoning and continue in a new chat. We'll follow one log-retention change through those steps. Product details reflect the September 23, 2026 source snapshot.

A larger window doesn't ensure the agent has read the right files. OpenAI's Codex guidance recommends supplying task-relevant files and examples.

ANTHROPIC / SEPTEMBER 22, 2026

Claude Opus 5.5

1Mtoken context window

Anthropic describes Opus 5.5 as a model for long coding sessions. Its context guidance still warns that longer inputs can reduce recall.

A model can hold more information and still miss the detail your task depends on.

Provider API limits. Effective limits depend on the client and configuration. GitHub lists both models as generally available in Copilot as of September 23.

There are two separate questions here: did the evidence reach the model, and can it use that evidence reliably? A large window answers neither by itself. OpenAI's Codex guidance addresses the first by asking for task-relevant files and examples. Anthropic warns about the second: recall can fall as inputs grow. The OpenAI source is general workflow guidance, not a measured recall limit for Astra. These figures are provider API limits; Copilot may expose a different effective limit.
CONTEXT / WHAT THE MODEL RECEIVES

Your prompt shares space with the session

The prompt is only part of the input

The next response uses the context the client sends. That can include earlier messages, file reads and tool results, or summaries of older turns.

  • Old instructions can remain after the task changes.
  • Large tool outputs can take up much more space than your request.
  • When the window fills, VS Code summarizes older conversation history.
The right-hand list shows possible inputs, not a guarantee that every earlier message arrives unchanged. Clients can select, truncate or summarize history. The practical point is that your latest request shares space with material gathered along the way, including work that may no longer be relevant. VS Code shows context usage in the Chat input and compacts older history when the window fills. A summary saves space, but it may leave out a detail you still need.
CONTEXT / FAILURE MODES

How useful context gets lost

01 / MISSING

Some evidence is missing

A search returns 100 matches. The relevant module is in the results that weren't shown.

RiskThe agent misses an exception

02 / NOISE

The chat fills with old work

Failed attempts and long logs remain after they've stopped helping with the task.

RiskImportant details are harder to use

03 / DISTRACTION

An old pattern looks reusable

A nearby module uses a legacy convention. The agent copies it without checking whether it still applies.

RiskThe change follows the wrong convention

When an answer is wrong, check what the agent saw as well as what it did.

These problems call for different responses. Missing evidence needs another search or file read. Old session history may call for a fresh chat. A misleading example needs a check against the current requirement. A legacy module isn't automatically wrong, but copying it without understanding the exception is risky. Context is one place to investigate a bad result; it isn't an explanation for every model error.

A longer chat can make details harder to find

CHROMA / 2025

Across 18 models, longer inputs often reduced accuracy on controlled tasks.

SHI ET AL. / 2023

Irrelevant sentences reduced accuracy on the math problems tested.

LIU ET AL. / 2023

Bars are conceptual, not measurements. The studies tested earlier models, not the two models shown earlier in this talk.

The bars illustrate what can accumulate; they don't measure how quickly noise grows. The studies below them show several ways long or distracting inputs affected earlier models. Chroma found that the effect varied by model and task. More context can also help when it contains evidence the task needs. The goal is to keep useful information available and remove material that no longer helps, rather than make every prompt as short as possible.

02 / RPI
R→P→I→R

Carry the findings
into the next phase

RPI records what you've learned and decided.
A new chat can pick up from those files.

Context engineering means choosing the information an agent needs for its next step.

Summary of the idea discussed by Andrej Karpathy and Tobi Lutke, June 2025
The useful idea behind context engineering is to choose the information needed for the next step. Tobi Lutke and Andrej Karpathy helped popularize that framing. RPI applies it to a software change: investigate first where evidence is missing, write a plan, make the change and compare the result with the requirements. The written records let another chat or another person continue without reconstructing the entire conversation.

Use the files to carry decisions forward. Research runs when evidence is missing; adequate existing evidence can be reused.

Read-only research means it doesn't change project source. It does write findings and a Planning Readiness record. Planning turns the evidence and decisions into tasks, then gets one critique of the final candidate. Implementation changes the code and records the checks it ran. Review compares those results with the plan and decides what still needs work. The filenames are shortened here; the actual records use dated folders and task names under .copilot-tracking. A file handoff makes a fresh chat possible, but doesn't start one automatically.

Wider→Deeper→Contrarian

Illustrative findings and evidence IDs. Subagents are optional in every RPI phase as of September 18 (#2902).

Notice the difference between an exception and a limit. The two legacy names are a finding. The fact that only variable declarations were checked is a limit on the investigation. Planning is not ready while the naming decision remains unresolved. Each research cycle goes Wider to find relevant areas, Deeper to inspect the details, then Contrarian to look for evidence against the emerging answer. C and W IDs let the reader trace findings to code or external sources. A helper can suggest where to look; the researcher still verifies the source.
PLAN / CRITIQUE

Write tasks you can verify

M log-retention-plan.md Illustrative excerpt
#### [ ] P01-T01: Add log retention
Goals:
* All 14 modules accept log_retention_days.
Requirements:
* FR-001: Default to 30 days.
* FR-002: Accept only 1 to 365 days.
* FR-003: Keep prefix in legacy modules (D1).
Details:
* Follow the pattern in modules/blob.
References:
* Research C1, C2; decision D1
Dependencies:
* None

Keep the details with the task

Put the goal, requirements and source references together, so the implementer can find them without retracing the investigation.

Here, a value of 0 must fail in every module, including the two legacy modules.

rpi-plan-critique assesses the final plan once: Pass, Revise or Blocked.

A useful task says what must hold when it's done. Here, adding a variable isn't enough: the default and range must be correct in all 14 modules, and the existing prefix names must remain. P01-T01 gives feedback a specific task to refer to. The full plan also includes a summary and before-and-after diagrams. The critique checks the final candidate against the evidence. The planner resolves the findings rather than rerunning the critique in search of a pass.

An optional way to work. RPI records live in dated folders under .copilot-tracking/, which is gitignored in HVE Core.

You don't have to clear the chat at every phase. Do it when the history is making the next step harder. Before leaving, check that the files include the decisions and evidence the next phase needs. Then reference those files in the new chat. VS Code's context-engineering guide recommends this for implementation and review. Compaction is another option when you want to continue the same chat, but a summary is not a complete copy of the conversation.
IMPLEMENT / REVIEW

Check the change against the plan

IMPLEMENT
  • Follow approved tasks in dependency order.
  • Mark a task done only when its requirements hold.
  • Record the changes and check results in changes.md.
  • Update the plan when a discovery changes the work. Pause tasks that depend on it.
REVIEW / ONE RECORD PER RPI TASK
  • Code misses a requirement→rpi-implement
  • A decision is missing→rpi-plan
  • Evidence is missing→rpi-research
  • Work remains outside scope→follow-up item
Execution: CompleteOutcome: Defects found

Example statuses. Complete means the review finished. The outcome tells you whether the result meets the plan.

Implementation records what changed, which checks ran and what remains unverified. Review then compares that evidence with the requirements. A code defect goes back to implementation; a missing decision belongs in planning; missing evidence calls for research. Work beyond the agreed scope becomes a separate follow-up. The review's execution can be Complete while its outcome is Defects found. That distinction prevents a finished review from being mistaken for an accepted change. A later fix does not require another Review of the same RPI task.

Example selection. Safety confirmations, required gates and human review apply in every mode.

TRADE-OFFS

Use RPI when the work needs investigation

USE RPI
  • The change spans files or modules you don't know well.
  • Different modules follow different conventions.
  • You need a record of decisions or dependencies.
  • Someone else will continue or review the work.
USE A DIRECT EDIT
  • The change is clear and isolated.
  • You could describe the diff in one sentence.
  • Existing evidence and checks are enough.

You can also use one phase skill, such as /rpi-research, without the full workflow.

Check the assumptions

A written requirement can still be wrong.

Allow for the extra work

Research and review take time. Use them where they help.

Human review still matters

Read the findings and plan before approving the change.

RPI adds work, so use it where the investigation and written decisions are worth that effort. A change across unfamiliar modules is a good candidate. A clear, isolated edit may need only the edit and its checks. Both HVE and provider guidance leave room for that smaller path. You can also use research or planning on its own. If you choose the coordinated workflow, its required checks and safety boundaries still apply; a shorter task is not permission to bypass them.
