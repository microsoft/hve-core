This talk covers why the context a model sees still matters now that GPT-6 Astra and Claude Opus 5.5 offer million-token windows, and how the current HVE Core RPI workflow manages that context. The first chapter shows how context goes wrong. The second walks through the four RPI phases and the files that carry context between them. ANTHROPIC / SEPTEMBER 22, 2026

Claude Opus 5.5

1Mtoken context window

Built for long-running agentic coding. Anthropic's guidance: more context is not automatically better, because accuracy and recall degrade as tokens grow.

Capacity grew. The next decision still depends on what reached the context: complete or partial, current or stale, relevant or distracting.

API figures from provider documentation. Effective limits depend on the client and model setup. Both models are listed as generally available in GitHub Copilot.

Both providers made large capacity gains this month, and their own documentation still treats context quality as the constraint. OpenAI's GPT-6 guide says Astra is more coherent on long tasks, asks when input could change the result, and is more sensitive to instructions in skills and files it can read. Anthropic calls the degradation context rot and says curating context matters as much as the available space. In the March workshop, the discussion was about windows growing from roughly 10K to 200K tokens; the frontier is now about one million.
CONTEXT / ONE GROWING LOG

The whole session steers the next action

The model reads one growing log

Each message and tool call adds to it. The next action is chosen from all of it, including what is stale or unrelated.

  • After a long session, your request is a small share of the log.
  • Tool output usually dominates: file reads, search results and terminal logs.
  • When the window fills, VS Code compacts the history into a summary.
Anthropic's context-window documentation lists what counts: the system prompt, every message, tool results, images, documents and tool definitions. Claude Code's guidance makes the same point about files read and command output. The rows are categories that accumulate together, not steps in order. VS Code shows usage in the context window control in the chat input and compacts the conversation automatically when the window fills.
CONTEXT / FAILURE MODES

Three ways context misleads a model

01 / MISSING

Evidence never arrives

Search and read tools return a bounded slice. The model decides from what came back.

ResultDecides on partial evidence

02 / NOISE

Useful context gets diluted

Old reads, failed attempts and long logs stay in the session and compete for attention.

ResultLoses precision over time

03 / DISTRACTION

Wrong examples look right

A legacy pattern, a similar file or a conflicting instruction competes with the intended one.

ResultFollows a plausible, wrong pattern

The output looks like a model error. The cause is often what reached the context.

These are the three failure modes this talk is about. Missing evidence comes from bounded tools; the next slide shows the actual VS Code limits. Noise builds up in long sessions; Claude Code's documentation calls out the kitchen-sink session and repeated corrections. Distraction is the hardest to spot because the wrong context looks relevant: an older module, a similar file or an instruction that conflicts with the task. OpenAI notes that GPT-6 Astra follows instructions in files it can read more closely, which makes a stale or conflicting instruction more consequential.

What the model has to notice

  1. 212 of 312 matches were never shown.
  2. The long file stopped at line 2,000.
  3. No tool fetches the rest on its own. The agent decides whether to ask again.

If the match that matters is number 101, it is not in context until the agent asks for it.

Fictional repository. Search defaults to 100 results with a 200-result cap, both experiment-based settings; read_file stops at 2,000 lines. Other hosts use different limits.

Both behaviors come from the VS Code 1.139.0 source released on September 23. grep_search collects more matches than it shows, then reports how many it found and how many it is showing, grouped by file. The alternative tag format reports, for example, 100 matches (more results are available). read_file truncates at 2,000 lines and at 2,000 characters per line, and tells the model to continue with offset and limit. These limits keep one call from flooding the context. They also mean the model works from partial evidence unless it follows up. The March workshop showed the same effect with the earlier 200-match output.
NOISE AND DISTRACTION

Noise grows faster than evidence

CHROMA / 2025

18 models lost accuracy as input grew, with the task held constant.

SHI ET AL. / 2023

Irrelevant details in a problem cut reasoning accuracy sharply.

LIU ET AL. / 2023

Bars are conceptual, not measurements. The studies tested earlier models; Anthropic's current guidance says the effect appears across models, more gently in some.

The bars are a conceptual picture carried over from the March workshop, not measured percentages. The research strip is the evidence. Chroma held task difficulty constant and still saw accuracy fall as input grew across 18 models, with distractors affecting models unevenly. Shi and colleagues showed that irrelevant sentences in math problems substantially reduce accuracy. Liu and colleagues showed that models use information in the middle of long inputs less reliably. These studies evaluated earlier model generations. Anthropic's current documentation describes the same effect, context rot, for its current models.
CASE / MARCH 2026 WORKSHOP

A finished file is not a correct result

  1. Broad requestFind how tracking files are used, repo-wide.
  2. Searches fill the windowWide searches and full reads used most of it.
  3. A fast helper summarizesAn Explore subagent returned condensed findings.
  4. Re-reading to fill gapsThe main agent re-read files to recover detail.
  5. Compaction mid-writeHistory was summarized as the file was written.
  6. Document deliveredIt existed, but was inaccurate and incomplete.

What RPI changes

  • Research scopes the question and records what it covered.
  • Helper returns are leads. The researcher verifies them at the source.
  • Verified findings go into the research file as they arrive, so compaction cannot erase them.

One session with earlier model and client versions, reconstructed as a diagram. An observation, not a benchmark.

In the March 2026 workshop, a request to document how Copilot tracking files are used across microsoft/hve-core went wrong. The session used Claude Opus 4.6 in VS Code; the built-in Explore subagent ran on Claude Haiku 4.5. Broad searching filled the context, the subagent returned a condensed summary, the main agent re-read files and ran low on space, and compaction ran while it was writing. The result was a file with inaccurate and missing details. Claude Code's documentation calls this pattern the infinite exploration: an unscoped investigation that reads hundreds of files. Current RPI research answers it with a scoped question, recorded coverage, verification of helper returns and incremental writes to the research file.
02 / RPI
R→P→I→R

Give each phase
the context it needs

Research, Plan, Implement and Review each leave a file.
The next phase starts from that file, not the whole chat.

“…filling the context window with just the right information for the next step.”

Andrej Karpathy on context engineering, June 2025
Context engineering is Andrej Karpathy's phrase for filling the context window with just the right information for the next step; Tobi Lutke described it as providing all the context for the task to be plausibly solvable. RPI applies the idea to software changes: each phase has a narrow job, writes its result to a file, and the next phase can start from that file in a fresh chat.

Guarding against missing evidence

  • It cannot edit code, so its job is evidence.
  • Every finding cites C# codebase or W# external evidence and states its limits.
  • Helper results are leads. The researcher verifies them at the source.
Wider→Deeper→Contrarian

Sample evidence IDs. Since September 18 (#2902), no RPI phase requires a subagent.

Research is read-only. Each executed cycle runs three waves: Wider for breadth, Deeper for detail and Contrarian for counter-evidence. Findings map to C# codebase and W# external evidence IDs in an Evidence Log, with confidence and limits, and Planning Readiness records whether planning can proceed. A research helper such as RPI Researcher is optional; it returns source pointers and excerpts as suggestions, and the researcher verifies them before recording evidence. That rule answers the workshop session, where a condensed summary stood in for evidence.
PLAN / CRITIQUE

Plan turns evidence into checkable tasks

M log-retention-plan.md Illustrative excerpt
#### [ ] P01-T01: Add log retention
Goals:
* Storage modules accept log_retention_days.
Requirements:
* FR-001: defaults to 30 days.
* FR-002: rejects values outside 1 to 365.
* FR-003: legacy modules keep prefix (D1).
Details:
* Follow the pattern in modules/blob.
References:
* Research C1, C2; decision D1
Dependencies:
* None

Why this helps the implementer

The task carries its own goals, requirements and references. The implementer reads this, not the whole research log.

Requirements make the result checkable.

rpi-plan-critique reads the final plan once, with fresh eyes: Pass, Revise or Blocked.

The plan opens with an executive summary and a Phase Checklist with before-and-after Mermaid diagrams; the excerpt shows one task block. Stable IDs such as P01-T01 survive edits to the file, so you can refer to them in feedback. The critique is a separate, read-only assessment of the final plan against the supplied evidence. The planner addresses its findings and records their disposition; the critique is not repeated.

Use /clear or a new chat between phases or tasks, or after repeated corrections.

Resume from files

Open or reference the file and its task ID, such as P01-T01.

Compact with care

/compact keeps the chat, but its summary can drop details. VS Code also compacts when the window fills.

RPI files live in dated folders under .copilot-tracking/, which is gitignored. A reset is a tool for clarity, not a required step.

Resetting is optional; use it when the chat no longer helps the next action. Claude Code's guidance is blunt: after two failed corrections, clear and start again with a better prompt. VS Code's context engineering guide recommends saving a plan to a file, opening a new chat that references it and reviewing in a fresh chat against the plan. RPI's files make that routine. The research, plan, critique, changes and review records carry the evidence, and stable task IDs let a fresh chat pick up where the last one stopped.
IMPLEMENT / REVIEW

Implement to the plan, review against it

IMPLEMENT
  • Works through approved tasks in plan order.
  • Checks a task only when its requirements hold.
  • Records changes and validation in changes.md.
  • Significant discoveries update the plan before dependent work continues.
REVIEW / ONE RECORD PER TASK
  • Implementation defect→rpi-implement
  • Decision gap→rpi-plan
  • Evidence gap→rpi-research
  • Residual work→follow-up item
Execution: CompleteOutcome: Defects found

Example statuses. Review keeps execution (Complete, Partial or Blocked) separate from outcome, so finishing a review never implies passing it.

Implementation follows the current task-centered plan. When new information changes the plan, it updates the affected tasks after any required decision and pauses only dependent work. The changes log describes behavior that changed, not every edit. Review compares the evidence in one pass and writes RV-xxx findings with proposed routes; a later fix does not trigger another review of the same task. Claude Code's guidance adds a caution: a reviewer asked to find gaps usually reports some, so act on those that affect correctness or the stated requirements.

TRADE-OFFS

Use RPI when context is the risk

USE RPI
  • The change spans files or modules you don't know well.
  • Searches return more than one page of results.
  • Decisions, dependencies or risks need a record.
  • Someone else will continue or review the work.
USE A DIRECT EDIT
  • The change is clear and isolated.
  • You could describe the diff in one sentence.
  • Existing evidence and checks are enough.

Need only one step? Run that phase skill, such as /rpi-research.

It records evidence

A wrong requirement stays wrong until someone questions it.

It takes time

Each phase adds a step. Skip phases the task doesn't need.

It needs your review

Read the research and plan before approving them.

Provider guidance supports both columns. Codex's guide says a strong model can do useful work with minimal setup, and recommends planning for complex, ambiguous or hard-to-describe tasks. Claude Code says plan mode adds overhead and to skip it when you could describe the diff in one sentence. Anthropic's advice is to do the simplest thing that works. HVE Core's own RPI documentation recommends a smaller direct edit for clear, isolated changes and research only for a demonstrated gap.
